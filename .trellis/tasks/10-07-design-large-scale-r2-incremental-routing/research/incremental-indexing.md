# 大规模 R2 增量索引与处理

**范围：** 设计研究，不修改业务代码，不执行真实 R2 操作。

## 结论

1. 1–2 TB 不是每次轮询都必须重新读取的量。真正昂贵的是当前实现对每个 `.tar.gz` 再次读取归档流来找模型。
2. 新归档的模型名只存在于归档成员路径时，第一次处理该归档仍必须读取归档内容；不能只靠 `ListObjectsV2` 的对象元数据识别模型。
3. 稳态应采用“事件发现为主、元数据轮询校准为辅”。事件只把新增或被覆盖的对象放入待处理队列；对象指纹已成功处理时不再读取归档。
4. 当前 JSON 文件存储适合任务报告，不适合高频对象索引和并发工作队列。单容器 MVP 应使用挂载卷上的 SQLite（WAL 模式）保存对象指纹、模型关联、路由任务和重试状态。

## 当前代码的性能瓶颈

`backend/r2_client.py::list_source_objects` 会分页列举全部对象，把全部结果收集到内存后排序。`backend/app.py::run_scan_job` 随后按对象串行调用 `scan_object_with_retries`。扫描器只跳过非 `.tar.gz`，对归档使用流式 `tarfile` 读取成员路径；它不会落盘解压，但为了确认所有模型，最坏情况仍需要读完整个归档。

因此，现有“持续扫描”如果简单改成每隔几分钟重复调用当前接口，会反复承担：

- 全桶对象列举和分页耗时；
- 全部历史归档的网络读取；
- 同一归档的重复模型识别；
- 大量报告 JSON 重写和进程内任务占用。

R2 的服务端 `CopyObject` 已避免归档经过 FastAPI 转发，但它只解决复制链路，不能解决模型识别链路。

## 对象指纹和状态

对象索引至少使用：

```text
(source_bucket, object_key, fingerprint)
fingerprint = ETag + size；必要时加入 LastModified 或版本 ID
```

ETag 是版本变化线索，不应在 multipart 场景下当作通用 MD5。对象写入事件或列表元数据不能证明归档内部模型，模型列表必须在一次归档读取后保存。

建议状态：

```text
seen -> queued -> scanning -> classified -> routing -> copied
                         |-> unmatched
                         |-> awaiting_mapping
                         |-> retry_wait -> failed
                         |-> skipped_existing_target
```

对象识别和路由要分开记录。这样目标映射改变时，可以复用已有模型识别结果，不再读取归档；没有目标桶时保留 `awaiting_mapping`，保存映射后补发路由任务。

## 三种发现方式

| 方式 | 每次成本 | 新对象发现 | 适合程度 |
|---|---|---|---|
| R2 `object-create` -> Queue | 只处理事件对象 | 秒级异步，至少一次投递 | 主路径，需配置 Queue、DLQ 和消费者 |
| 定时 `ListObjectsV2` | 仍需列举所有对象，但不必读取 body | 轮询间隔内发现 | 校准和事件不可用时的降级路径 |
| 仅依赖 `LastModified`/continuation token | 不能取得真正的变更游标 | 可能漏掉字典序靠前的新 key 或覆盖 | 不能单独作为可靠增量方案 |

`ListObjectsV2` 的 continuation token 只能继续一次分页过程，不是跨轮询变更游标。若没有事件通知，轮询仍要从头列举元数据，再用 `(key, fingerprint)` 与索引比较；它比读取 1–2 TB 便宜很多，但对象数非常大时仍需安排较低频率、分页 checkpoint 和告警。

## 历史数据初始化

历史对象无法凭空获得模型索引。推荐：

1. 先配置事件规则和 Queue，再启动一次全量回填，避免回填期间漏掉新对象。
2. 回填只把列表元数据分批写入 SQLite，使用 checkpoint，不把全桶对象保存在一个 JSON 报告中。
3. 对未处理的 `.tar.gz` 设置有限并发，扫描器流式读取并保存模型列表。
4. 识别完成后立即生成路由任务，使用现有服务端 `CopyObject`；目标 key 已存在则保持当前“不覆盖”规则并记录跳过。
5. 回填结束后执行一次元数据对账，合并事件期间新增或发生变化的对象。

不能承诺完全不做一次全量历史扫描：如果模型名只在归档内部，首次识别 1–2 TB 数据就是必要成本。可以做到的是“只做一次、可断点、可限速、之后不重复读”。

## 持续处理与幂等

Queue 采用至少一次投递，重复事件和乱序事件都必须正常。事件先写入 SQLite，再确认 Queue；归档读取和复制不应占用 Queue 的可见性租约。重复 `(bucket, key, fingerprint)` 直接复用已分类结果或合并待处理任务。

对于同一 key 被覆盖的情况，新 fingerprint 应被视为新版本候选。当前系统不覆盖目标同名对象，因此新版本到达后应报告 `target_exists_source_changed` 或进入人工处理队列，不能静默把旧目标当成最新数据。若业务确认源桶只追加唯一 key，可以把该情况作为低频告警。

失败重试应区分：网络、超时和暂时性目标权限问题可重试；归档损坏应记录为终态；目标桶没有映射应等待配置。所有失败记录只保存安全分类和次数，不写入凭据或完整供应商响应。

## 对当前仓库的实施建议

- `backend/r2_client.py`：增加事件对象元数据、HEAD/条件读取和分页列表接口；保留现有 CopyObject。
- `backend/storage.py`：新增 SQLite 对象版本表、模型关联表、路由任务表和重试字段；JSON 继续保存面向用户的报告。
- `backend/scanner.py`：复用现有单对象识别函数，改为事件/队列任务输入；不解压落盘。
- `backend/sync.py`：按对象版本生成幂等路由任务，明确“不覆盖”的版本冲突结果。
- `backend/app.py`：增加 Queue 拉取器、有限并发 worker、周期对账、启动恢复和停机处理。
- `config.py`/部署：连续运行不能依赖页面临时输入的 R2 凭据。应通过部署密钥或外部 Secret 注入 R2 凭据和 Queue API token，绝不写入 data volume。
- 前端：增加“持续分流”开关、队列积压/失败/最后对账时间和暂停按钮；手动全量扫描保留为恢复工具，不作为日常增量路径。

## 推荐顺序

第一阶段先实现“对象版本索引 + 手动增量任务 + 定时元数据对账”，验证幂等和路由状态；第二阶段接入 R2 Event Notifications -> Queue -> HTTP pull；第三阶段才开启自动 CopyObject。这样即使事件配置尚未就绪，也能用对账任务发现新对象，不会直接把自动复制暴露到未经验证的状态模型上。
